# repsynth

The representation synthesis harness: representations (number systems, encodings, scripts, instruction
extensions) are chosen by specification, and the software, instructions and hardware that depend on them are
regenerated by existing tools (QEMU, GNU binutils and GCC, Verilator, GHDL, Yosys, nextpnr, APCISR) and held to
one set of vectors.

## One command

    ops/run.sh --iteration I1        # builds the kept containers once, then runs the iteration inside them
    ops/run.sh --iteration I1 --native   # on a build machine that already carries the tools

Iterations are listed in plan/iterations.csv; each has ops/iterations/<N>.steps. Progress is live; a rerun
resumes without repeating completed steps. RESUME.md and docs/index.html are regenerated at the end.

## The command-line tool

    python3 -m repsynth doctor [--build]
    python3 -m repsynth spec check spec/reps/numeric/*.yaml
    python3 -m repsynth vectors
    python3 -m repsynth gen                 # Ninja over the dependency graph
    python3 -m repsynth impact d --confirm  # DEP-05 change (d): pair to planes trit encoding
    python3 -m repsynth conform --lane software
    python3 -m repsynth selftest
    python3 -m repsynth report

## Layout

As MRD section 9.8: spec/ (schema, representations, reference functions), gen/ (generators per target),
graph/ (edges, slices, build.ninja), conformance/ (vectors, runners, mutants), lanes/, containers/, ledger/,
reports/, records/, docs/ (status page), ops/.
